# MyAgent · 目标与实现方式

> 一个不用任何 agent 框架、从空目录开始、逐文件手写的生产级 agent。
> 项目名 **MyAgent**，Python 包名 **agentlab**。

---

## 1. 目标

### 1.1 一句话

实现一个能真正干活的命令行 agent：给它一句自然语言，它能自己读文件、改代码、跑命令、看报错、再改，直到任务完成。

```
$ agentlab "把 agentlab/ 里所有 print 换成 logging，然后跑测试"
  ↳ read_file   agentlab/client.py
  ↳ edit_file   agentlab/client.py
  ↳ bash        pytest -q
  ↳ 读失败输出 → 再改 → 通过
```

### 1.2 真正的目标不是"最强的 agent"

现成的 agent 框架很多。这个项目的价值在于**每一行代码都看得懂、每一个决定都有理由、每一步都能验证**。

所以有两个硬约束：

1. **不依赖任何 agent 框架**（LangChain / LlamaIndex / LangGraph / AutoGen 一律不用）。
   只用标准库 + 少量基础设施库（HTTP 客户端、终端渲染、JSON Schema 校验）。
2. **不写"魔法"**。没有任何"框架帮你处理好了"的黑盒。prompt 拼装、工具调用解析、上下文压缩、权限校验、失败重试，全部自己写。

### 1.3 "生产级"的验收标准

| 维度 | 具体要求 |
|---|---|
| 可观测 | 流式输出、每步耗时、token 账本 |
| 可恢复 | 会话落盘，进程重启能续跑 |
| 安全 | 路径收敛在工作区内；写操作/执行命令需审批 |
| 健壮 | 网络错误分类重试；工具失败不弄死主循环；超时保护 |
| 可测 | 不联网也能跑完整循环（假模型客户端） |
| 可扩展 | 加一个工具 = 加一个类；换模型厂商 = 加一个适配器 |

## 2. 总体架构

依赖方向**严格向下**，下层不知道上层的存在。

```
┌──────────────────────────────────────────────────────────┐
│ cli.py          REPL、流式渲染、审批交互                   │  L7
├──────────────────────────────────────────────────────────┤
│ loop.py         主循环：调模型 → 执行工具 → 回填 → 再循环   │  L3
├───────────────┬───────────────┬──────────────────────────┤
│ context.py    │ policy.py     │ session.py               │  L4/L5/L6
│ 历史与压缩     │ 权限与路径守卫 │ 持久化与续跑              │
├───────────────┴───────┬───────┴──────────────────────────┤
│ llm/   模型适配器      │ tools/  工具注册表与内置工具       │  L1/L2
├───────────────────────┴──────────────────────────────────┤
│ types.py + events.py   数据契约 + 事件流（零依赖）         │  L0
└──────────────────────────────────────────────────────────┘
```

**L0 是最关键的**：`types.py` 不 import 任何东西，`events.py` 只 import `types`。因此测试可以纯内存构造对象，不需要网络、不需要 API key。

## 4. 关键设计决策

每一条都是"不这么写就会出事故"，不是风格偏好。

### 4.1 数据契约先行

先定 `Message` / `ContentBlock` / `Completion` 的形状，再写逻辑。原因：agent 的 bug 八成出在数据结构上——工具结果和调用对不上号、历史里塞了半截 JSON、重试时把已发出的消息改脏。

### 4.2 内部消息模型直接对齐 OpenAI

> 2026-11-18 修订：原方案是"厂商中立"（选 Anthropic 形态、把 OpenAI 差异推到适配器）。
> 后来判定：实际要接的是 DeepSeek / Kimi / vLLM 这类 **OpenAI 兼容服务**，
> 内部的"中立形态"等于凭空多一层翻译，每种翻译都是一类 bug 的来源。
> 于是改为内部直接说 OpenAI 的话，代价是以后接 Anthropic 要写反向适配器。

内部只认三种内容块：`TextBlock`、`ToolCallBlock`、`ToolResultBlock`，且形态就是 OpenAI 的：

- 角色 `system` / `user` / `assistant` / `tool`
- 工具调用是 `tool_calls`，参数 `arguments` 保留 JSON 字符串原文
- 一条工具结果 = 一条 `role="tool"` 消息（批量构造时 `Message.from_tool_results` 返回元组）
- `Usage.cached_input_tokens` 对应 `prompt_tokens_details.cached_tokens`

`StopReason` 仍用语义名（`end_turn` / `tool_use` / `max_tokens` / `refusal`），
但映射表写死在 `types.py` 的文档字符串里：`stop` / `tool_calls` / `length` / `content_filter`。

### 4.3 过程（Event）与结果（Message）分离

`Message` 是要发给模型的东西，必须持久化、可回放。`Event` 是过程广播（"正在生成"、"工具开始跑"），可以丢。

混用是最常见的架构错误：一旦把 UI 关心的状态塞进 prompt，模型会被无关噪音干扰，token 也白烧。

### 4.4 工具失败是"数据"，不是"异常"

工具是模型的外设。外设坏了，正确做法是把故障翻译成模型能读懂的一句话：

```
文件不存在: src/a.py（可用 list_files 查看目录）
参数校验失败: text 应为 string，收到 integer
执行超时（>30s），可以缩小范围重试
```

模型读到这些会自己换条路。**抛异常穿透主循环，等于剥夺了模型自我修复的机会。**

### 4.5 参数校验统一在注册表做

每个工具自己写 `if "path" not in args` 一定会漏。统一用 JSON Schema 校验，错误信息精确到字段，工具作者不用重复劳动。

### 4.6 重试策略：已经吐过字就不重试

流式响应中途失败时，若已经向用户输出了文字，重试会让内容出现两遍；更糟的是，若前半截已触发工具调用，重试等于**把副作用执行两遍**。

因此重试只发生在"还没吐出任何内容"时。

### 4.7 并行工具执行但结果顺序保真

模型经常一口气发 3-4 个独立调用。串行等是 4 倍延迟，所以并发执行；但结果回填顺序必须与调用顺序严格一致——顺序一乱，模型会把"读 A 的内容"当成"读 B 的结果"，直接产生幻觉。

### 4.8 工具结果必须一次性整批回填

OpenAI 要求每个 `tool_call` 都有对应的 `tool` 响应，缺一个就 400。所以一批工具执行完，一次性塞进一条消息。

### 4.9 上下文必须有预算和压缩

长任务会撞上下文上限。这不是靠重试能解决的，必须由 `context.py` 主动压缩（保留最近 N 轮 + 关键工具结果摘要）。

### 4.10 路径收敛是安全底线

`../../etc/passwd`、`/etc/shadow`、指向外部的软链接——所有路径先 `resolve()` 再校验是否在工作区内。这是 agent 的牢笼，不是可选项。

### 4.11 命名：声明用 Definition，转换用 encode/decode

> 2026-11-19 定案，改过一次名。

- 给模型看的工具说明书叫 `ToolDefinition`，不叫 `ToolSpec`——它是**声明**，不能执行；
  将来可执行的工具叫 `Tool`（`tools/base.py`）。定义与实现成对命名。
- 适配器的转换函数叫 `encode_messages` / `encode_tools` / `decode_response`，
  不用 `to_openai_xxx`：源和目标在名字里都看得见，将来 `anthropic_compat` 复用同一套动词。
- 模型一次调用的完整结果叫 `Completion`，**刻意不改**：它贴着 OpenAI 协议
  （`/chat/completions`、`completion_tokens`），换成 `ModelResponse` 反而丢掉这层对齐。
  与 4.2 同源的原则：**协议形态贴近协议，语义判断用自己的词**（如 `StopReason`）。

### 4.12 工具结果：字符串 + 两个本地标记，超长砍中间

`ToolResult` 只有三个字段：`content`（给模型看的文本）、`is_error`（本地语义，协议里没有）、
`truncated`（本地可观测性）。刻意不做成"任意对象 + 事后序列化"：

- 模型只能读文本，结构化值进 prompt 前总得序列化一次，不如在工具里做完；
- 工具作者因此被迫想清楚"这个输出打印出来，模型能看懂吗"。

截断超过 24k 字符时砍**中间**：报错结论在末尾，`import` 与定义在开头，砍中间丢的信息最少。
切口**对齐行边界**——半行会让模型以为结构到此为止（`def foo(x):` 后面跟 `    ret`），
据此去改文件必然匹配失败。`head_ratio` 可按工具调（`bash` 偏尾部、`grep` 偏头部）。

但这只是**兜底**。真正的解法是工具自带分页（`read_file` 的 offset/limit），长输出一开始
就不该整段塞进上下文；截断只负责"绝不撑爆"，不负责"让模型找回被砍的部分"。

### 4.13 验收靠"跑起来"：主入口 + 客户端，不靠断言

> 2026-11-20 定案：根目录 `main.py`（FastAPI + uvicorn）作服务入口，仓库不保留测试目录。
> 此前写过一版 4 个真实网络集成测试，验证 M1 通过后按决定删除。

- **每落地一个能力就重启服务、发一条真实请求**：看完整往返——模型输出、token 账、延迟、
  工具到底有没有被调用。这一阶段要回答的是"它能不能用"，断言回答不了。
- **接口文档与代码同源**：请求/响应模型写成 `BaseModel` + `Field(description=...)`，
  FastAPI 自动生成 `/docs`，浏览器里点按钮就能发请求，不用记 curl 参数。
- **端点一个个长出来**，不一次铺满：`/health` → `/chat`（单轮）→ `/tools`（注册表）→
  `/agent`（多轮循环）→ `/chat/stream`（SSE）。每加一个都当场跑通再进下一个。
- **代价**：没有回归保护，改坏了靠人发现。这个代价被明确接受，M5 再补自动化测试。

## 5. 开发方式

**一次只加一个文件，一个文件只解决一个问题。**

每个文件的固定流程：

1. 讲清楚它解决什么问题、不解决什么问题
2. 写代码（尽量短，注释写"为什么"而不是"是什么"）
3. **现场跑一遍**，贴真实输出
4. 讲调用关系：谁调它，它调谁
5. 通过后才进入下一个文件

已经能跑的代码绝不推倒重来；发现设计错误时，宁可多花一轮重构，也不在上面继续叠加。

## 6. 技术选型

| 选择 | 理由 |
|---|---|
| Python 3.11+ | 类型注解、`match`、`asyncio` 生态成熟；代码短，适合讲原理 |
| `httpx` | 异步 + 流式（SSE）支持好；不用官方 SDK 是为了看清协议本身 |
| `jsonschema` | 工具参数校验的事实标准 |
| `rich` | 终端流式渲染、Markdown、语法高亮 |
| `python-dotenv` | 本地读 `.env` |
| `pytest` + `pytest-asyncio` | 测试 |
| `uv` | 依赖安装与虚拟环境（比 pip 快一个数量级） |

运行环境：WSL2 Ubuntu 24.04 + Python 3.14 + venv。
