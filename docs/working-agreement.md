# MyAgent · 协作约定

> 记录"怎么跟我一起写这个项目"，不是技术设计。
> 技术上的取舍见 [goal-and-design.md](goal-and-design.md)，进度见 [progress.md](progress.md)。
>
> 最后更新：2026-11-18

---

## 1. 开发节奏

- **一次只加一个文件，一个文件只解决一个问题。**
- 每个文件的固定顺序：讲清它解决什么 → 写代码 → **现场跑一遍** → 讲调用关系。
- **不预先铺开整个模块的骨架。** 曾经一次性生成 12 个文件、2100 行、58 个测试，能跑但读不懂，最后整体推倒重来。宁可多花几轮，也不要一次给一堆看不懂的代码。

---

## 2. 怎么介绍一个新生成的文件

用户明确要求的讲法，按这个顺序说：

1. **一句话说它解决什么问题、不解决什么问题。**
2. **逐个说"这个决定为什么这么定、代价是什么"** —— 只说真正有取舍的点，不复述代码。
3. **贴真实运行输出**（成功输出和真实报错都要）。
4. 最后给两块：**故意没做的事** + **下一步是什么**。

不要做的事：

| 不要 | 原因 |
|---|---|
| 先讲整体架构图 / 分层图 / 项目定位 | 已经讲过，重复一遍只会稀释重点 |
| 按行号平铺 200 行细节 | 用户会直接说"过于复杂"；需要时再逐行展开 |
| 用"这体现了设计哲学"代替具体理由 | 空话 |
| 把同一个设计点讲三遍（在三个小节里各说一次） | 噪音 |

**正确的口吻**：像刚写完把文件递过去，坐在旁边讲一遍——"这个文件就干一件事，里面两样东西，第一样是……"。不是写规格说明书。

---

## 3. 复杂度控制

- 默认简洁。术语第一次出现时用一句人话解释。
- **一个文件里不要塞第二件事**：契约文件里不写重试循环，数据结构文件里不写序列化。
- 用户说"太复杂了" → **这是讲法问题，不是代码问题**：不要重写代码，换口吻重讲。
- 用户说"重新吧" → 同一份内容换讲法重来，**不要加新内容**。

---

## 4. 每个文件必须有真实输出

- 不许说"应该能跑"、"理论上可以"。
- 讲解里必须贴真实执行结果，包括失败时的真实报错原文。
- 验证脚本可以放 `/tmp`，不进仓库（保持仓库只有项目文件）。

---

## 5. 文档冲突要摆出来

设计与进展文档不一致时（例如 `goal-and-design.md` 说拆成 `llm/base.py` + `llm/openai_compat.py`，而 `progress.md` 说单文件 `client.py`），**先说明冲突、给出选择和理由，再动手**。不要默默选一条往前走。

---

## 6. 基础结构类的自由度

- `types.py` 属于**基础结构**：字段宁可一次加全（如 `role="tool"`、缓存命中字段），避免后面反复改契约。
- 但每加一项都要写清"为什么现在加"。契约改动比业务代码贵。

---

## 7. 协议对齐

- 内部数据形态**优先对齐 OpenAI 协议**（`role` 四种、`tool_calls`、`arguments` 为 JSON 字符串），因为要接的是 DeepSeek / Kimi / vLLM 这类 OpenAI 兼容服务。
- 语义化的名字可以保留（如 `StopReason` 用 `end_turn` / `tool_use`），但**必须写清与 `finish_reason` 的映射**，否则以后接第二家厂商会踩坑。

---

## 8. 提交

- 一个逻辑改动一次提交。
- 标题：`type: 一句话中文摘要`；正文分段说明"改了哪些文件、为什么"。
- 只提交仓库内容，`.venv` / `__pycache__` 不入库。
- 提交前确认 `ruff check` 与 `mypy` 通过。

---

## 9. 反馈信号对照表

| 用户说 | 意思是 |
|---|---|
| 太复杂了 | 讲法问题，不是代码问题 |
| 重新吧 | 换口吻重讲同一内容，别加料 |
| 撤回改动 | 先恢复工作区，再回到讲解 |
| 这个文件我已经理解了 | 清空包袱，进入下一个文件 |
| 一点一点扩充框架 | 继续按"一个文件一个功能"推进，不要跳步 |
